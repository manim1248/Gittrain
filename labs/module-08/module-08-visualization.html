Artifacts & Caching — hand off outputs, reuse dependencies

Artifacts move build outputs between jobs; the cache reuses dependencies across runs. Simulate both below. Companion to guides/module-08-artifacts-and-caching.md.

8.1 Artifact hand-off — build → upload → download (ADO: PublishPipelineArtifact / DownloadPipelineArtifact)

Each job is a fresh runner. To pass files from build to deploy you upload an artifact, GitHub stores it (90 days default), then a later job downloads it. Watch the hand-off.

Job: build
npm run build → dist/
→
upload-artifact
name: webapp-dist · path: dist/
→
GitHub storage
stored as zip · 90 days
→
Job: deploy
download-artifact → files restored
— Console —

Generated YAML (the two actions that matter)

# job: build
      - name: Upload build output
        uses: actions/upload-artifact@v4
        with:
          name: webapp-dist
          path: dist/
          retention-days: 14
          if-no-files-found: error
# job: deploy (needs: build)
      - name: Download build output
        uses: actions/download-artifact@v4
        with:
          name: webapp-dist
          path: dist/
Matrix gotcha: a matrix job uploading under one artifact name: overwrites per combination. Use a unique name — name: ${{ matrix.service }} — or omit name: to download all.

8.2 Artifact vs job output — what are you passing? (strings = job outputs, files = artifacts)

Only pass files as artifacts. A single string (image tag, version) travels via job outputs — cheaper and instant. Click each hand-off type to see the right mechanism.

String — image tag, version, path
Job output: outputs: image-tag: ${{ steps.tag.outputs.tag }} → consumed as needs.build.outputs.image-tag
Files — compiled dist, test report, container artifact
upload-artifact / download-artifact — a later job (or a person) consumes the files
Dependencies — node_modules, go module cache
Cache — keyed restore, LRU eviction, must never be required for correctness

8.3 Cache key simulator — hit, miss, and restore-keys (ADO: Cache@2 task key/restoreKeys)

The cache is keyed. An exact key hit restores instantly; a changed lockfile changes the key (miss), but restore-keys: still salvages the closest previous cache. Change the lockfile and watch.

Exact key
key: linux-npm-<hash>
restore-keys fallback
prefix: linux-npm-

  
Golden rule: the cache is an accelerator — a cache miss must never fail your build. And never cache secrets; the cache store is not a secrets vault.






  
8.4 Decision guide — which mechanism? 

  

    
ArtifactBuild OUTPUT a later job or person consumes → upload/download-artifact

    
Job outputJust a string (tag/version) → needs..outputs

    
CacheDependencies/intermediates to speed up a rebuild → actions/cache or setup-* cache flag

    
Setup-action cachecache: npm on setup-node — one flag, no manual keys — recommended default

  

  
Monorepo tip: setup-node with cache: npm looks at the repo root lockfile. In a multi-service repo, set cache-dependency-path: services/<name>/package-lock.json so each service's cache keys off its own lockfile.
