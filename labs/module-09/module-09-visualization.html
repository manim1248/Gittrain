9.1 The container pipeline — run it (ADO: Docker@2 task)

The four stages every container workflow goes through. Run the simulation, then read the exact YAML below.

1 · Build
buildx · BuildKit · layer cache
→
2 · Tag
metadata-action → branch + sha tags
→
3 · Authenticate
login-action · GHCR token
→
4 · Push
build-push-action · push: true
— Console —

What the YAML looks like (the 4-action pattern)

# push to main → build, tag, push to GHCR
permissions:
  contents: read
  packages: write          # ← required for GHCR
steps:
  - uses: actions/checkout@v4
  - uses: docker/setup-buildx-action@v3
  - uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}
  - uses: docker/metadata-action@v5
    id: meta
    with:
      images: ${{ vars.IMAGE_REGISTRY }}/${{ github.repository }}
      tags: |
        type=ref,event=branch
        type=sha,format=short
  - uses: docker/build-push-action@v6
    with:
      context: services/checkout
      file: services/checkout/Dockerfile
      push: true
      tags: ${{ steps.meta.outputs.tags }}
      cache-from: type=gha
      cache-to: type=gha,mode=max

9.4 Hand-off to GitOps — where Actions' job ends (Flux takes over; out of scope)

Boundary reminder: this course's scope ends at the manifest reference update. Do not have Actions kubectl apply directly — that bypasses your GitOps model. With sha-based tags, every push produces a unique immutable reference Flux can reconcile and you can roll back.
