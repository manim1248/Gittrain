17.1 The troubleshooting workflow (no ADO equivalent — this is a Copilot-native loop)

The loop that turns a wall of text into a merged fix.

Identifyfind failing run & job (Module 16)
Copy log tailfailing step, last ~50 lines
Prompt Copilotlog + workflow file + repo context
Diagnosiswhy did it fail — before any fix
Fix as diffminimal, PR-ready YAML
Review & verifyModule 15/13 guardrails, then re-run
The whole game is context. A log alone is ambiguous; a log + workflow file + repo = a fix Copilot can be held accountable for. Copilot Chat can read files from the workspace — point it at .github/workflows/.

17.5 Strengths & limits (what to trust, what to escalate)

  

    

      
Copilot is strong at

      
    
        
  • Explaining cryptic error text (exit codes, action errors)
    • 
        
  • Spotting YAML syntax / schema errors (indentation, bad keys)
    • 
        
  • Matching a log pattern to a known cause (auth, cache, timeout)
    • 
        
  • Suggesting the idiomatic action/pattern to replace a hack
    • 
        
  • Generating a diff you can review
    • 
      

    

    

      
Not for / weak at

      
    
        
  • Knowing the current state of a live cluster/registry
    • 
        
  • Live debugging on a self-hosted runner
    • 
        
  • Ops judgment — "is this safe to deploy?"
    • 
        
  • Final sign-off on security / permissions (Module 15)
    • 
        
  • Knowing your org's approval rules (Modules 13/14)
    • 
      

    

  

  
Escalation rule: if Copilot cannot explain an error confidently, that's a signal to check the environment (registry, runner, OIDC config) rather than the workflow — a confident-but-wrong explanation usually means the context was too thin.
