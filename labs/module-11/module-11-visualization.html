Deployment Integration — where GitHub Actions' job ends

Build → push image → update manifest reference. Then Flux reconciles the AKS cluster. Click through the hand-off boundary to see exactly what Actions owns — and what it must not touch. Companion to guides/module-11-deployment-integration.md.

The one rule: Actions writes to git (and the registry). Flux writes to the cluster. If Actions ever runs kubectl apply, you've created two sources of truth.

11.2 Mechanisms for updating the manifest reference (ADO: commit-to-GitOps ≈ release trigger to a deployment repo)

Three ways to tell Flux a new image exists. Click each to see the trade-off. The recommended default is the controlled commit.

1 · Git commit / PR from the workflow
Actions edits the image line in the manifests repo and pushes. Auditable, keeps "git as source of truth".
2 · repository_dispatch / webhook to Flux
Actions signals "new image available"; Flux image automation or a receiver reconciles.
3 · Flux Image Automation
Flux polls the registry and bumps its own manifest. Fully GitOps-native — zero Actions involvement (Flux mechanics, out of scope).






  
11.3 The controlled commit — a working hand-off job (ADO: this job ≈ the release step that updated the deployment repo)

  
This is the pattern to replicate: build & push, then a separate job with contents: write that bumps the manifest in the GitOps repo with a bot identity.

  

  
Anti-pattern to catch in review: a kubectl apply step anywhere in this workflow. That bypasses Flux and breaks the GitOps model.
