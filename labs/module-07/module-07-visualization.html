Workflow Control for Multi-Service Repos — don't rebuild what you didn't touch

Click files in the monorepo tree, build a matrix, and wire up a job graph. See how path filters, matrix strategy, if: conditions, and needs keep a many-service CI lean. Companion to guides/module-07-workflow-control-multi-service-repos.md.

7.1 Path filters — which workflows fire? (ADO: trigger path filters)

Workflows declare paths: so a push only triggers the services it touches. Click files in the repo tree to simulate a push and see which workflows start.

Repo tree (click a file)

monorepo/ ├── .github/workflows/ │ ├── checkout-ci.yml │ ├── orders-ci.yml │ └── payments-ci.yml ├── services/checkout/ │ ├── src/app.ts │ └── Dockerfile ├── services/orders/ │ └── src/handler.ts └── services/payments/ └── package.json

Workflow paths: patterns: checkout-ci.yml → services/checkout/**, orders-ci.yml → services/orders/**, payments-ci.yml → services/payments/**. Changes to .github/workflows/*.yml always trigger all workflows.

Push result

The silent-skip trap: a push that matches no paths: never starts the workflow and never posts a status check. Teams then wonder why CI "didn't run" — it was correctly skipped.

7.4 concurrency & timeouts — control the chaos (ADO: cancel previous + job timeouts)

  

    
concurrencygroup: ci-${{ github.ref }} — one active run per branch

    
cancel-in-progressnew push supersedes the running one — saves minutes on busy repos

    
timeout-minutesjob default 360 min; set 15–20 for CI. A hung test no longer pins a runner for 6 hours

    
step timeouttimeout-minutes on a single step caps even one hung command

  

  
Rule: every job in a multi-service workflow should carry an explicit timeout-minutes. Matrix jobs multiply — a hung combination costs you N runners at once.
