GitHub Actions Architecture — interactive execution model

Click an event, run the pipeline, and watch how event → workflow → job → step → runner fit together. Companion to guides/module-01-github-actions-architecture.md.

1.1 The execution model — run it (ADO mapping: stages → jobs → tasks)

An event starts a workflow (the YAML). The workflow defines jobs, each job runs on its own fresh runner and executes ordered steps. Steps may be shell commands or reusable Actions.

1 · Event
Something happened on GitHub — push, PR, cron, manual click
→
2 · Workflow
.github/workflows/ci.yml matching the event is loaded
→
3 · Job
Unit of work; needs links jobs; parallel by default
→
4 · Steps
Ordered commands / Actions; a failing step stops the job
→
5 · Runner
Ephemeral machine (ubuntu-latest). Wiped after each run
— Console · click an event to start —

1.2 Workflow file anatomy — click any block

Every workflow file declares what should happen. Click a highlighted block to see what it does and how it maps from ADO.

name: CI
on:
  push:
    branches: [main]
  pull_request:
permissions:
  contents: read
env:
  NODE_VERSION: '20'
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
      - run: npm ci
      - run: npm run build
        if: ${{ github.event_name == 'push' }}

1.3 Where did “stages” go? (structural ADO mapping)

ADO pipelines are stages → jobs → tasks. GitHub Actions has no stages key — teams express the same idea three ways. Choose the one that matches your intent.

1.4 GitHub-hosted vs self-hosted runners (≈ MS-hosted vs private agents)

AutomaticGitHub-hosted: provisioned per run, patched by GitHub
EphemeralFresh OS image every run — never treat it as persistent
Public netGitHub-hosted can't reach your VNet. Self-hosted can
Label-scopedSelf-hosted selected via runs-on: label — secure it well
For this course (AKS microservices): GitHub-hosted for CI (build/test/scan). Self-hosted only when you need private-network access, persistent state, or specialised hardware — e.g. a runner inside your cluster/VNet for the GitOps hand-off deployment job in Session 3.
