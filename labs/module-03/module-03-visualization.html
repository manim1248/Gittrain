Jobs, Steps & Execution Control — watch a pipeline run

Simulate needs scheduling, probe if: status functions, and generate a matrix. Companion to guides/module-03-jobs-steps-execution-control.md.

3.1 DAG simulator — parallel & dependent jobs

Jobs run in parallel by default; needs: makes one wait for another. Simulate both. Click a job bar to fail it and watch downstream react.

Click a bar mid-run to inject a failure 
jobs:
  lint:
    runs-on: ubuntu-latest
  test:
    needs: lint              # waits for lint
    strategy:
      matrix: { node: [18, 20, 22] }   # 3 parallel test jobs
  build:
    needs: lint              # independent of test → parallel with it
  docker:
    needs: [test, build]     # waits for both
  deploy:
    needs: docker
    environment: production  # approval gate (Module 13)

3.2 if: expression explorer

The four status functions control whether a step/job runs after upstream results. Choose a scenario.

Upstream resultalways()success()failure()cancelled()
Success✓✓✗✗
Failure✓✗✓✗
Cancelled✓✗✗✓
Patterns: always() → cleanup/summary steps · failure() → notifications · cancelled() → release queued runners · most steps should keep the implicit success() (no if: at all). Use continue-on-error: true when a non-blocking check should not fail the job.

3.3 Matrix builder

Pick Node versions and OSes — a matrix expands into one job per combination.


  

  
Concurrency control — limit simultaneous runs per branch:
concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true } — the older run for the same ref is cancelled and its runner freed (badges: queued ⇒ bar shown amber).
