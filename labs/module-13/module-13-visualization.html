Environments & Approval Gates — who may deploy, and from where

A named gate + config bundle per target: required reviewers, deployment branches, wait timers, and environment-scoped secrets. Companion to guides/module-13-environments-approval-gates.md.

13.1 What an environment bundles (ADO: environment + stage approvals + env-scoped variables)

An environment is not a server — it's a protection gate plus scoped configuration. Click each rule to inspect it.

13.2 The approval flow — step through a gated deploy (ADO: manual validation check on a stage)

A job that declares environment: production pauses before its first step until protection rules pass.

Team reviewers: if the required reviewer is a team, any member's approval satisfies the gate — the whole team doesn't have to approve. The run actor cannot approve their own run.

13.4 The workflow — environment on each job (same file deploys every env)


  
Same immutable image, different manifest refs. You never rebuild per environment — each gated job re-points the manifest reference. Environment-specific secrets (PROD_URL, per-env ACR creds) resolve only when the run targets that environment.






  
13.5 Environments + OIDC (the Module 12 bridge) & Copilot checkpoint

  
The environment name flows into the OIDC subject claim — a prod identity that literally cannot be used from a dev run.
